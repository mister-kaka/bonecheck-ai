# Анализ задачи

Фиксирует понимание ТЗ на 2026-09-18. Не описывает реализацию модели.

В этом git-репозитории **нет** PDF/Notion файла официального ТЗ. Источники:

- публичная постановка ЛЦТ 2026 (AI-сервис оценки качества исследований плотности костей);
- письменные ответы организаторов команде (локальный файл вне репозитория);
- эмпирика по датасету (анализ вне этого репозитория: `docs/dataset_analysis.md` / `Датасет.md` в рабочей папке хакатона).

---

## Цель

Построить AI-сервис оценки **качества** денситометрических исследований (DXA, DICOM CR, аппарат GE Lunar Prodigy Advance).

Оценивается корректность укладки и полнота визуализации зоны интереса.

Сервис **не** ставит клинический диагноз и **не** измеряет МПК / T-score.

Постановщик: Департамент здравоохранения Москвы, Центр диагностики и телемедицины.

---

## Пользовательский сценарий (продукт)

1. Пользователь передаёт DICOM-изображение.
2. Система анализирует качество.
3. Система определяет типы нарушений укладки (если есть).
4. Пользователь видит результат и найденные ошибки.

Веб-интерфейс в ТЗ как обязательная форма сдачи **не** расписан по экранам. Команда делает UI для демонстрации. Статусы `processing` / `completed` - решение команды, не текст ТЗ.

## Входные данные

CONFIRMED:

- исследования с одного типа аппарата: Lunar Prodigy Advance;
- формат в выданном наборе: DICOM CR;
- исследование в датасете может содержать несколько изображений;
- тестовый набор - тот же тип исследований;
- в DICOM нет PixelSpacing; для геометрии из ТЗ использовать фиксированный масштаб.

Масштаб (ответы организаторов):

| Ось | Размер пикселя |
| --- | --- |
| X | 0.6 мм |
| Y | 1.05 мм |

---

## Выходные данные

Для **каждого входного изображения** (правило: 1 строка таблицы = 1 файл):

| Поле | Смысл | Обязательность |
| --- | --- | --- |
| `quality_class` | `0` корректное, `1` есть нарушение качества | CONFIRMED, основное |
| `violation_type` | текст; несколько нарушений через `;`; пустая строка если нарушений нет | CONFIRMED |
| `quality_prob` | вероятность нарушения в `[0; 1]` | CONFIRMED как опциональное (для ROC-AUC) |

Правило агрегации качества: если хотя бы один критерий нарушения равен 1, изображение некорректно. На итоговый столбец исходной таблицы **нельзя** опираться как на единственный источник истины (были ошибки агрегации).

Допустимые `anatomical_region` (если поле используется):

- `Поясничный отдел позвоночника`
- `Проксимальный отдел бедра`

Сторона бедра (лево/право) в этом поле не кодируется. Нельзя опираться на суффиксы имён файлов в закрытом тесте.

---

## Допустимые `violation_type`

Поясничный отдел позвоночника:

- Некорректная укладка
- Не выравнена ось позвоночника
- Присутствуют посторонние предметы

Проксимальный отдел бедра:

- Некорректная укладка
- Некорректная область интереса

В ТЗ упоминаются 6 критериев, для метрик фактически 5 типов: позиционирование и ротация бедра объединены.

Macro-F1 считается по этому закрытому списку.

«Корректность области интереса» - полнота визуализации зоны, не ROI-разметка денситометра.

## Ограничения и запреты

CONFIRMED организаторами:

- не выявлять сколиоз, переломы, эндопротез, люмболизацию как ошибки качества;
- bounding box / маски для метрик не обязательны (достаточно факта нарушения);
- белые полосы разметки аппарата не основная задача;
- чёрные прямоугольники на снимках - маскирование мягких тканей, не признак нарушения;
- ось позвоночника - по центрам тел позвонков, вертикаль = ось изображения;
- решение должно работать **локально**; нельзя отправлять изображения во внешние API / облачные модели;
- решение должно укладываться в вычислительные ресурсы из ТЗ (точные цифры оборудования в этом репозитории **не лежат** - TBD, сверить с PDF ТЗ);
- репозиторий решения публичный, без передачи личных паролей.

Разрешено: внешние датасеты и предобученные модели, если inference локальный.

---

## Требования к качеству и оценке

Организаторы оценивают поэтапно:

1. Бинарная корректность изображения (`quality_class`).
2. Типы нарушений (отдельные и агрегированные метрики).

Если `quality_class=1` верен, а тип нарушения нет: общая метрика качества растёт, метрики по нарушениям падают.

Ошибка в типе при верном классе не «обнуляет» этап 1.

## Подтверждено ТЗ

Только то, что сказано организаторами / в постановке (см. разделы выше):

- цель - качество укладки DXA, не диагноз;
- поля результата и словари нарушений;
- 1 файл = 1 строка выхода;
- один тип аппарата и пиксельный масштаб;
- локальный запуск, без облачного inference;
- этапы метрик;
- патологии не являются violation.

## Принято командой

- монорепозиторий BoneCheck AI / RUEN;
- NestJS + React + Python;
- веб-сценарий загрузки одного файла и поллинга статуса;
- mock ML до готовности модели;
- in-memory метаданные, файлы на диске;
- датасет и веса не в git;
- UI для демонстрации (макет у frontend-команды, в репозитории ещё заглушка).

Текущий backend **не** считает метрики и **не** выдаёт таблицу на весь тест. Он отдаёт JSON на один загруженный файл.
