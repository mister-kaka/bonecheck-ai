# Архитектурные решения

Только решения, которые уже приняты или явно открыты. Статусы: CONFIRMED (есть в ТЗ или в коде), DECISION (команда), ASSUMPTION, TBD.

---

## Монорепозиторий

Статус: CONFIRMED

Контекст:
Нужен один способ отдать экспертам frontend, backend, ML и Docker.

Решение:
Один репозиторий https://github.com/mister-kaka/bonecheck-ai с каталогами `frontend/`, `backend/`, `ml/`.

Почему:
Проще клонировать и запускать. Не нужно согласовывать версии нескольких репозиториев.

Влияние:
Общий README и `docker-compose.yml` в корне.

## NestJS + отдельный Python ML

Статус: CONFIRMED (код) / DECISION

Контекст:
Нужны REST для UI и стек для DICOM / CV.

Решение:
Прикладной API - NestJS. Обучение и inference - Python-сервис.

Почему:

Влияние:

## PostgreSQL не в этом этапе

Статус: DECISION (сейчас) / PLANNED (замена)

Контекст:
Нужно хранить статус и результат между запросами UI.

Решение:
Интерфейс `StudyRepository`, реализация `InMemoryStudyRepository`. PostgreSQL готовится как следующая замена, в Compose её нет.

Почему:
Схема результата ещё может уточняться HTTP-контрактом ML. Подключение БД - зона инфраструктуры, не блокер API.

Влияние:
Перезапуск backend стирает исследования. См. [database.md](database.md).

## DICOM на диске, не blob в БД

Статус: CONFIRMED (код)

Контекст:

Почему:
Проще отдать путь в inference. Объектное хранилище избыточно для хакатона.

Влияние:
Нужен диск (и позже общий volume с ML). **TBD:** как Python-контейнер увидит файл.

## Единица inference и единица API - один файл

Статус: CONFIRMED (ТЗ) + DECISION (API)

Контекст:
Организаторы: одна строка выходной таблицы = одно изображение. В датасете разметка study-level (папка), а не file-level.

Решение:
`POST /api/studies` принимает **один** DICOM. Поля результата относятся к этому файлу.

Почему:
Совпадает с правилом таблицы. Веб-сценарий «загрузить снимок - получить оценку» проще пакетной загрузки.

Влияние:
Пакетный zip/папка исследования в API **не** реализованы (**PLANNED**, если понадобится для сдачи таблицы). Имя `study` в URL не равно study-папке датасета.

## Статусы исследования

Статус: DECISION

Контекст:
ТЗ не описывает статусы веб-приложения.

Решение:
`uploaded` | `processing` | `completed` | `error`. После успешной загрузки MVP сразу ставит `processing` (статус `uploaded` в enum есть, в ответах POST сейчас не встречается).

Почему:
Четыре состояния хватает для опроса прогресса.

Влияние:
Frontend должен поллить `GET /api/studies/:id`.

## Backend вызывает ML только через MlClient

Статус: CONFIRMED (код)

Контекст:
Модель Кирилла ещё не подключена.

Решение:
Интерфейс `MlClient`. Сейчас `MockMlClient`: пауза `ML_MOCK_DELAY_MS` (по умолчанию 300 мс) и фиксированный ответ `quality_class=0`, пустой `violation_type`.

Почему:
Формат полей уже из ТЗ, UI не ждёт финальную модель. Замена на HTTP-клиент не ломает контроллеры.

Влияние:
Демонстрация UI возможна без модели. Метрики качества по mock считать нельзя.

## Лимит файла 50 МБ

Статус: DECISION

Контекст:
Нужна защита от слишком больших upload.

Решение:
`MAX_FILE_SIZE_BYTES = 50 * 1024 * 1024` в коде. Multer отдаёт 413 `FILE_TOO_LARGE`.

Почему:
DICOM CR в датасете значительно меньше. Запас для аномалий.

Влияние:
Переменная `.env.example` `MAX_FILE_SIZE_BYTES` **не читается** кодом. Источник истины - константа.
