# Архитектура RUEN

## Обзор

Система строится как три независимых сервиса в одном монорепозитории.

```text
┌─────────────────────┐
│  Frontend (React)   │  интерфейс врача / эксперта
└──────────┬──────────┘
           │ REST JSON
           ▼
┌─────────────────────┐
│  Backend (NestJS)   │  API, оркестрация, валидация запросов
└──────────┬──────────┘
           │ HTTP (внутренний контракт, будет добавлен позже)
           ▼
┌─────────────────────┐
│  ML Service (Python)│  inference качества DXA-исследований
└─────────────────────┘
```

## Назначение слоёв

### Frontend

Отвечает только за интерфейс:

- загрузка исследования (будет добавлена позже);
- отображение статуса качества и нарушений;
- вызов REST API backend.

Frontend не содержит ML-логики и не обращается к Python-сервису напрямую. Это упрощает CORS, аутентификацию (когда появится) и контракт для экспертов: один публичный API.

### Backend (NestJS)

Прикладной слой:

- публичный REST API;
- OpenAPI/Swagger (`/api/docs`);
- health-check для проверки живости решения;
- будущая интеграция с ML-сервисом (проксирование файлов, таймауты, маппинг ошибок);
- будущая сборка выходной таблицы решения (по одному ряду на изображение).

Backend не обучает модель и не парсит DICOM на постоянной основе: тяжёлая обработка остаётся в Python.

### ML Service (Python)

Независимый inference-сервис:

- препроцессинг DICOM;
- загрузка весов;
- предсказание `quality_class` и `violation_type`;
- опционально `quality_prob`.

Изоляция Python-стека (PyTorch, pydicom, OpenCV) от Node.js снижает риск конфликтов зависимостей и позволяет масштабировать inference отдельно.

## Текущее состояние каркаса

| Сервис | Реализовано сейчас |
| --- | --- |
| Frontend | страница-заглушка и placeholder статуса backend |

| ML | структура пакетов и Docker-заглушка без модели |

## Принципы, которые нельзя нарушать при развитии

1. Датасет и веса моделей не коммитятся в git.
2. Клиническая диагностика патологий (сколиоз, переломы, эндопротез) не является целевым выходом MVP.
3. Единица выходного результата — одно изображение (один DICOM-файл), а не исследование целиком.
4. Публичный контракт для экспертов живёт на backend; ML — внутренний сервис.
